# Frozen `verl/` Diff Audit

This note audits the vendored `verl/` runtime against upstream `verl`
`v0.3.0.post0` and `v0.3.0.post1`.

Upstream sources used:

- https://github.com/verl-project/verl/archive/refs/tags/v0.3.0.post0.zip
- https://github.com/verl-project/verl/archive/refs/tags/v0.3.0.post1.zip

## Summary

The current `verl/` runtime is not a lightly patched copy of either
`v0.3.0.post0` or `v0.3.0.post1`.

- `verl/version/version` in this repository is `0.3.1.dev`.
- `post0` and `post1` differ from each other in only 11 files under `verl/`.
- The current runtime differs from both tags in the same scale:
  - 23 unchanged files
  - 162 modified files
  - 44 added files
  - 25 deleted files
- In all 11 files where `post0` and `post1` differ, the current runtime differs
  from both tags.

This means the frozen runtime appears to include a broader later `verl` runtime
update, plus project-specific UMAD/IPPO changes. It should not be simplified by
directly reverting files to either post0 or post1.

## UMAD/IPPO-Required Changes

These changes are directly used by the current `marl/` code path and should be
kept.

### Removed: Token Confidence Path

Files:

- `verl/workers/actor/dp_actor.py`
- `verl/workers/fsdp_workers.py`
- `verl/utils/torch_functional.py`
- `marl/learners/ippo_learner.py`

Original purpose:

- The actor log-prob path previously returned an extra token-level confidence
  tensor.
- The FSDP worker previously included that tensor in the old-log-prob
  `DataProto`.
- The IPPO learner previously used that tensor for confidence statistics and
  optional confidence-based advantage gains.

Cleanup decision:

- The current public UMAD/IPPO configuration uses `use_log_prob_gain=True` and
  does not enable confidence-based advantage gains.
- The confidence path was an intermediate algorithm-development branch rather
  than part of the current core UMAD training recipe.
- The path has been removed from `marl/` config, `marl/learners`, and the
  vendored `verl` actor/FSDP log-prob API.

### Multi-Turn Loss Mask Support

Files:

- `verl/workers/actor/dp_actor.py`
- `verl/trainer/ppo/ray_trainer.py`
- `marl/utils/marl_utils.py`

Purpose:

- PPO updates and GRPO advantage calculation can use `loss_mask` instead of only
  the response attention mask for multi-turn trajectories.

Keep rationale:

- UMAD debate trajectories are multi-turn and need the trainer to avoid charging
  loss to non-agent or non-response regions.

### Rollout and Validation Dump Hooks

Files:

- `verl/trainer/ppo/ray_trainer.py`
- `verl/trainer/config/ppo_trainer.yaml`
- `marl/ippo_trainer.py`
- `eval/debate_evaluator.py`

Purpose:

- `trainer.rollout_data_dir` and `trainer.validation_data_dir` enable JSONL
  dumps of training and validation generations.

Keep rationale:

- These dumps are used for academic debugging and reporting of debate
  trajectories.
- They also align with the public `eval/run_debate_eval.sh` output contract.

### Boxed Math Reward Compatibility

Files:

- `verl/utils/reward_score/__init__.py`
- `examples/data_preprocess/process_all_math.py`

Purpose:

- UMAD math prompts use boxed final answers.
- `DigitalLearningGmbH/MATH-lighteval` is routed to the math reward parser.
- GSM8K can be evaluated by the same boxed-answer parser in this path.

Keep rationale:

- `examples/data_preprocess/process_all_math.py` emits
  `DigitalLearningGmbH/MATH-lighteval` as the reward data source.
- Reverting this would break the math evaluation data generated by this release.

### TensorBoard Directory Injection

Files:

- `verl/utils/tracking.py`
- `bash/ippo_grpo.sh`
- `bash/run_single_agent_train.sh`

Purpose:

- TensorBoard output can be controlled through `marl.tensorboard_dir`,
  `trainer.tensorboard_dir`, or `TENSORBOARD_DIR`.

Keep rationale:

- The public training launchers pass `marl.tensorboard_dir`.
- This avoids writing TensorBoard logs to a hidden or personal default path.

Risk:

- If no path is injected, TensorBoard falls back to the relative directory
  `tensorboard_log`.

## Runtime Upgrade / Compatibility Changes

These are not clearly UMAD/IPPO algorithm changes. They look like broader
runtime drift beyond upstream `v0.3.0.post*`.

Keep for now unless a later upstream baseline is identified and tested:

- `models/mcore/*`
- `models/transformers/qwen2_5_vl.py`
- `tools/*`
- `utils/activation_offload.py`
- `utils/device.py`
- `utils/metric/*`
- `utils/reward_score/math_batch.py`
- `utils/reward_score/math_dapo.py`
- `utils/reward_score/sandbox_fusion/*`
- `workers/reward_manager/batch.py`
- `workers/reward_manager/dapo.py`
- `workers/rollout/async_server.py`
- `workers/rollout/schemas.py`
- `workers/rollout/sglang_rollout/*`
- `workers/rollout/vllm_rollout/vllm_async_server.py`
- `workers/sharding_manager/megatron_sglang.py`
- `third_party/vllm/vllm_v_0_5_4/*`
- `third_party/vllm/vllm_v_0_6_3/*`

The current runtime also removed older vendored vLLM backends:

- `third_party/vllm/vllm_v_0_3_1/*`
- `third_party/vllm/vllm_v_0_4_2/*`

These changes should be treated as dependency/runtime compatibility changes, not
as UMAD algorithm changes.

## Cleanup Candidates After Separate Testing

The following areas are not obviously required by the current default UMAD/IPPO
scripts, but should only be removed after import/runtime tests because they may
be referenced indirectly by `verl` backend selection:

- Megatron and mcore model conversion paths if the release is FSDP-only.
- SGLang rollout files if the release supports only vLLM text rollout.
- Sandbox Fusion tools if code-generation rewards are not part of the release.
- Qwen2-VL and vision dataset utilities if the release is text-only.
- DAPO/batch reward managers if only rule-based math rewards are supported.
- Unused vendored vLLM versions after confirming the supported vLLM version.

## Recommendation

Do not edit `verl/` directly as part of general open-source cleanup.

For a safe runtime cleanup pass:

1. Pick the real later upstream baseline that matches `0.3.1.dev` more closely
   than `v0.3.0.post0/post1`.
2. Recompute the diff against that baseline.
3. Preserve the UMAD/IPPO-required changes listed above.
4. Remove only runtime features that are proven unused by the public launchers
   and covered by smoke tests.
